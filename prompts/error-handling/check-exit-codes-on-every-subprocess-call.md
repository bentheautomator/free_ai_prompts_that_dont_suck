# Check Exit Codes on Every Subprocess Call

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents scripts that shell out, ignore the exit code, and build on top of commands that failed.

**[Copy-paste ready version](../../install/check-exit-codes-on-every-subprocess-call.md)** — just the instruction block, no explanation.

## The Problem

`subprocess.run(["pg_dump", db, "-f", backup_path])` — and on to the next line. If `pg_dump` fails (auth, disk full, wrong host), `subprocess.run` doesn't raise; it returns a `CompletedProcess` with `returncode=1` that nobody looks at. The script proceeds to compress an empty file, upload it, and log "backup complete." The same hole appears in every scripting context: bash scripts without `set -e` where a failed `cd` means the next command runs in the wrong directory, `os.system()` calls whose return value vanishes, Node `exec()` callbacks that use `stdout` without checking `error`.

Exit codes are the one error channel that requires explicit opt-in to even notice. Exceptions interrupt you; a nonzero return code just sits there. AI assistants, generating the happy path, treat the subprocess call like a statement that "does the thing" rather than an operation that reports an outcome — partly because `subprocess.run` without `check=True` is the most common form in training data, including in all the tutorials that were also wrong.

Shell-out failures are disproportionately nasty because subprocesses do heavy things: backups, migrations, builds, deploys, ffmpeg jobs. Ignoring their exit codes means the heavy thing silently didn't happen.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Check Exit Codes on Every Subprocess Call

Every external command's exit status MUST be checked, and a nonzero status must stop dependent work. A subprocess call without a checked exit code is an operation whose failure you have chosen not to know about.

- Python: use `subprocess.run([...], check=True)` so failure raises `CalledProcessError`; if you must inspect instead, branch on `result.returncode` explicitly. Never use bare `os.system(cmd)` without checking its return value
- Bash: start scripts with `set -euo pipefail` so failed commands, unset variables, and failed pipeline stages stop the script; for commands allowed to fail, make it explicit (`if ! grep -q pattern file; then ...` or `cmd || true` with a comment saying why)
- Node: check `error` in `exec`/`execFile` callbacks before touching stdout; with `child_process.spawnSync`, check `.status`; prefer promisified versions that reject on failure
- On failure, capture and surface stderr — `pg_dump: connection refused` is the actual error; "command failed with exit 1" alone is a context-free message
- Failure must abort dependents: don't upload the archive when the dump failed, don't restart the service when the build failed
- A command's success must be judged before its output is used; parsing stdout of a failed command processes garbage
- Pipelines hide failures: in bash, without `pipefail`, `cmd1 | cmd2` reports only `cmd2`'s status

**Red flags that you're about to violate this:**
- "subprocess.run executes it; that's what matters..."
- "These commands basically never fail..."
- "I'll grab stdout — if it ran, there's output..."
- "Adding check=True might break callers that expect no exception..."
- "The script is simple; it doesn't need set -e..."

## Why It Works

1. **It reframes the unchecked call as a decision.** "Failure you have chosen not to know about" converts an omission the model doesn't notice into a statement it has to stand behind.

2. **It names the exact flags and idioms.** `check=True`, `set -euo pipefail`, callback `error` checks — the failure is per-API muscle memory, so the correction must be per-API muscle memory too.

3. **It links exit codes to dependent work.** The cost of an ignored code is the next line running on a false premise; tying the check to "stop dependents" explains *why* checking matters, which survives paraphrase better than a bare rule.

4. **It legalizes intentional failure tolerance loudly.** Some commands are genuinely allowed to fail (`grep` finding nothing); requiring the explicit `|| true`-with-comment form keeps that case from becoming the loophole that unravels the rule.

## Origin

A release script generated by an assistant ran database migrations via a shell call, then restarted the application servers. The migration command had been failing for three releases — a permissions issue, printed plainly to stderr that nothing captured — while the script sailed on and restarted the app against an old schema each time. Release four included code that required the new columns. The resulting outage was traced backward through three "successful" deploys to a single `subprocess.run` missing `check=True`.
