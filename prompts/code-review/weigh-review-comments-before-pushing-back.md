# Weigh Review Comments Before Pushing Back

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents responding to a review by defending every flagged decision instead of genuinely weighing which comments are right.

**[Copy-paste ready version](../../install/weigh-review-comments-before-pushing-back.md)** — just the instruction block, no explanation.

## The Problem

A reviewer leaves eight comments. The assistant replies to all eight — with eight defenses. The variable name "is consistent with the local style." The missing test "is covered transitively." The questionable abstraction "allows for future flexibility." Each rebuttal is articulate, plausible, and generated by the same process: take the existing code as the conclusion, then construct supporting arguments. The review has become a debate in which the assistant is counsel for the defense, and the defendant is its own diff.

This happens because a language model asked "why is this code this way?" is exceptionally good at producing justifications — the code exists, so reasons for it are easy to generate, regardless of whether those reasons drove the original decision or whether they're any good. Without an explicit weighing step, fluent self-justification is the path of least resistance for every single comment.

The reviewer's experience: nothing lands without a fight. Each comment costs a round-trip argument against an opponent with infinite stamina and no ego on the line. Humans facing that adapt by commenting less — and the review process quietly dies while the threads stay polite.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Weigh Review Comments Before Pushing Back

For every review comment, ALWAYS evaluate "is the reviewer right?" before composing any defense of the current code. Your first output for each comment must be a verdict on the comment, not a justification of the diff.

You can generate a plausible defense of any existing code. That ability is exactly why "I can defend it" carries zero evidence about whether the comment is correct.

- For each comment, steelman it first: under what conditions is the reviewer right? Check those conditions against the actual code before drafting a word of response.
- Default to accepting comments that are cheap to apply and plausibly better, even when the current code is defensible. "Defensible" is not "preferable," and the reviewer's fresh eyes are data.
- Reserve pushback for comments that are factually wrong or whose fix causes concrete harm you can name. Then push back once, with specifics, and accept the human's call.
- Track your ratio across the review. If you're contesting most of a competent reviewer's comments, the most likely broken component is your weighing step, not their judgment.
- Never pushback-by-volume: a long reply to a short comment is a smell. If your defense needs four paragraphs, the code probably needs the change more than the thread needs the essay.

**Red flags that you're about to violate this:**

- "There's actually a good reason for each of the things they flagged..."
- "I'll explain my rationale on this one too, for completeness..."
- "Conceding too many comments makes the original work look sloppy..."
- "Their suggestion works, but mine also works, so no change needed..."
- "Let me write up why this design choice was deliberate..."
- "I'm not arguing, I'm providing context..."

---

## Why It Works

1. **It reorders the pipeline.** "Verdict on the comment before defense of the code" interrupts the model's default flow, where justification generation starts the moment the comment is read and consumes the slot evaluation should occupy.
2. **It explicitly devalues defensibility.** Naming the asymmetry — the model can defend anything, so a defense is evidence of nothing — disarms the rationalization engine with its own mechanism.
3. **"Cheap and plausibly better → accept" sets a decision rule** that resolves the most common case without a thread, reserving human attention for the few comments where disagreement is load-bearing.
4. **The ratio check is an outside view.** Per-comment, each rebuttal feels justified; across the review, contesting 7 of 8 is a statement about the responder. Making the model compute the ratio surfaces the pattern its per-comment reasoning hides.

## Origin

A staff engineer reviewed an assistant-authored caching layer and left nine substantive comments. All nine received courteous, detailed rebuttals citing flexibility, consistency, and intentional design. The engineer, out of patience for nine debates, escalated two and dropped seven. One of the dropped seven — "this lock scope looks wider than it needs to be" — was correct, and the contention it caused became a p99 latency incident during the next traffic spike. The postmortem's action item was about humans: "stop reviewing the agent's PRs solo."
