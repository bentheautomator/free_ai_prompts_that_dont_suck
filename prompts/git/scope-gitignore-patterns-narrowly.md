# Scope .gitignore Patterns Narrowly

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents the AI from adding sweeping ignore patterns that make new source files invisible to git, and from expecting .gitignore to affect already-tracked files.

**[Copy-paste ready version](../../install/scope-gitignore-patterns-narrowly.md)** — just the instruction block, no explanation.

## The Problem

Asked to stop git from noticing some generated JSON, an AI assistant adds `*.json` to `.gitignore`. Problem solved — and also every future config file, fixture, and manifest in the repo is now silently invisible. The developer who later creates `routes.json` will `git add .`, see nothing staged, commit anyway, and ship a build broken only for everyone else. Overbroad ignore patterns are time bombs: they don't fail when added, they fail months later as "works on my machine."

The second misunderstanding is direction: `.gitignore` only affects *untracked* files. Assistants routinely add a pattern for an already-tracked file, observe that `git status` still shows its changes, and then either declare the task done (wrong) or escalate to something destructive. Untracking requires `git rm --cached`; the ignore entry alone does nothing. Both failures come from treating `.gitignore` as a magic suppression list rather than a precise matching ruleset with specific semantics.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Scope .gitignore Patterns Narrowly

Write `.gitignore` patterns as narrowly as the actual problem requires. NEVER add a broad extension or wildcard pattern (`*.json`, `*.txt`, `data/`, `config*`) to handle one specific file or directory.

Overbroad patterns silently hide future legitimate files; the failure surfaces months later when someone's new file never makes it into a commit.

- Ignore the specific path, not the class: `build/output.json`, not `*.json`. Anchor patterns with a leading `/` when you mean the repo root (`/dist/`, not `dist/` which matches at any depth).
- Before adding any pattern, test its blast radius: `git status --ignored --short` after the change, or `git check-ignore -v <path>` on files that should NOT be ignored, to confirm they aren't.
- Adding a pattern does nothing to files already tracked. If the goal is to stop tracking a file, you need both the ignore entry and `git rm --cached <path>` (which keeps the file on disk), and the user should know the file will vanish from the repo for everyone else on their next pull.
- Never "fix" a noisy `git status` by ignoring whole directories you haven't inspected.
- Comment non-obvious entries: `# generated by scripts/export.py` costs one line and saves the next archaeologist an hour.

**Red flags that you're about to violate this:**

- "Ignoring all .json files covers this case and any like it."
- "I added it to .gitignore, so git will stop tracking it now."
- "A wildcard is more robust than listing specific files."
- "git status is noisy; ignoring this whole directory cleans it up."
- "Nobody will ever need to commit a file matching this pattern."

---

## Why It Works

1. **It reframes "robust" as the failure mode.** The AI generalizes patterns out of a tidiness instinct ("cover future cases too"); the rule points out that covering future cases is precisely the bug, since future cases include legitimate files.
2. **The `git check-ignore -v` test makes blast radius observable** at write time instead of discovery time, collapsing a months-long feedback loop into one command.
3. **Stating the tracked-file semantics removes a real knowledge gap** — much of this failure isn't carelessness but a wrong model of what `.gitignore` does, and one sentence corrects the model.

## Origin

To silence a generated lockfile, an assistant added `*.lock` to a repo's gitignore. Five weeks later a developer added a new dependency manifest lockfile, and `git add .` quietly skipped it. CI built green from the stale committed state; production resolved different dependency versions than every developer machine. The bug took two days to find because the broken layer was the one nobody reads: the ignore file.
