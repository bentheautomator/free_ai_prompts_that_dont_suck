# Never Claim Should Work, Run It Instead

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents the assistant from ending work on "this should work" when the check that would replace "should" with "does" is sitting right there.

**[Copy-paste ready version](../../install/never-claim-should-work-run-it-instead.md)** — just the instruction block, no explanation.

## The Problem

"This should work now." It's the most common closing line in AI-assisted coding, and it's a tell. "Should" means the assistant is predicting instead of observing — and the prediction is being offered in an environment where observation was available. The assistant has a shell. It could run the thing. It chose to forecast instead.

The word does real damage because it sounds like modest confidence when it actually marks an evidence gap. Users read "should work" as "works, with humility." The assistant means "I have not checked." Those are different states of the world, and the gap between them is exactly where the bugs live: the prediction is built from the same understanding that produced the code, so any misunderstanding that caused a bug also predicts the bug away.

Why does the assistant prefer forecasting? Because a prediction can't fail during the session. Running the check might surface a problem that demands more work; saying "should work" ends the turn successfully every time. The incentive gradient points away from verification unless something pushes back.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Never Claim Should Work, Run It Instead

NEVER end work with "should work," "ought to work," or any predicted outcome when you have the means to observe the actual outcome. If a check is available, the prediction is forbidden; run the check and report what happened.

The core problem: a prediction about your own code is generated by the same understanding that generated the code, so it inherits every bug. Only execution consults something outside your own head.

- When you catch yourself about to type "should," stop and identify the command that would convert it to "does": run the script, execute the test, hit the endpoint, evaluate the expression. Then run that command.
- Report observations, with their source: "ran <command>, got <result>." If the result was bad, say so and keep working — a true failure report beats a false success report every time.
- "Should work" is permitted in exactly one situation: you genuinely cannot execute the check from your environment. Then name the obstacle and hand the user the exact command to run, e.g. "I can't reach the staging database from here; run <command> and check for <expected output>."
- Apply this to all outcome predictions, not just the word "should": "this will fix it," "that ought to resolve the error," "it'll behave correctly now" are the same claim in different clothes.

**Red flags that you're about to violate this:**
- "This should work now — let me summarize what I changed..."
- "I'm confident enough that running it isn't necessary..."
- "Verifying would mean setting things up, and the change is small..."
- "The user can test it on their end..."
- "It will work because the logic mirrors the documentation example..."

---

## Why It Works

1. **It turns one word into a tripwire.** "Should" is reliably present at the exact moment of the failure, so binding the rule to the word catches the behavior precisely when it happens, with no judgment call required.

2. **It names the epistemic trap.** The prediction and the code share an author and therefore share their bugs. Once stated, "I'm confident" stops counting as evidence even to the model producing it.

3. **It makes failure a valid result.** Part of the pull toward "should work" is that running the check risks a bad answer. Explicitly ranking a true failure report above a false success removes that risk's sting.

4. **It defines the only legal escape.** Permitting "should" solely when execution is impossible, with the obstacle named, prevents the exception from quietly becoming the rule.

## Origin

A session closed with "Updated the cron schedule — the job should run at midnight now." It didn't, because the schedule string had six fields and the scheduler expected five, which the scheduler's own dry-run validator would have reported in two seconds. Nobody noticed for nine days, because "should work" reads like "works" when it's the last line on the screen. Nine days of a silent nightly job cost a quarter's worth of analytics backfill.
