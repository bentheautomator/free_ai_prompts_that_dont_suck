# Your Last Edit Is a Suspect, Not a Verdict

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents the AI from convicting (or acquitting) the most recent change without actually testing whether it caused the failure.

**[Copy-paste ready version](../../install/your-last-edit-is-a-suspect-not-a-verdict.md)** — just the instruction block, no explanation.

## The Problem

Something breaks right after a change, and the AI commits to one of two stories without evidence. Story one: "this must be from my edit" — so it starts mutating its own recent change, even when the failure is a flaky network call or a bug that was always there and just got exercised for the first time. Story two: "this failure is unrelated to my change" — so it dismisses a breakage its edit genuinely caused, usually because the failing file is one it never touched (forgetting that behavior travels through imports, shared state, and call graphs).

Both stories are guesses wearing confidence. The honest move is embarrassingly cheap: temporarily remove the recent change and re-run. If the failure persists, the edit is innocent; if it disappears, the edit is implicated. AI assistants skip this because it interrupts forward motion — stashing, re-running, and unstashing produces no new code, and the model's narrative momentum strongly prefers explaining over measuring.

Each wrong story has its own bill. Convicting an innocent edit means mangling a correct change to appease an unrelated failure. Acquitting a guilty one means shipping the breakage and starting a fresh debugging session next week with the causal link long gone from memory.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Your Last Edit Is a Suspect, Not a Verdict

NEVER assume the most recent change did or didn't cause a new failure. Test it: remove the change, re-run, observe. The recent edit is always the prime suspect and never the convicted, until that experiment runs.

"It broke right after my edit" is correlation. The causation check costs one stash and one re-run.

- When a failure appears after a change: stash or revert the change (`git stash`, `git checkout -- <files>`), run the same reproduction, and note whether the failure persists
- Failure persists without the change → the change is innocent; restore it and look elsewhere, instead of "fixing" correct code
- Failure disappears without the change → the change is implicated; restore it and find which specific part is responsible, narrowing if it's large
- Do not acquit your edit just because the failing code is in a file you didn't touch — effects propagate through imports, shared state, ordering, and data; the stash test covers all of those at once, your intuition doesn't
- Do not convict your edit just because the timing matches — first-time-exercised paths, external services, and pre-existing bugs all produce post-edit failures
- State the experiment's result ("fails on clean baseline too" / "passes without my change") before proceeding either way

**Red flags that you're about to violate this:**
- "This broke right after my change, so my change must be the cause..."
- "The failure is in a module I never touched, so it's unrelated..."
- "I'll just adjust my recent edit until this goes away..."
- "This looks like a pre-existing issue, moving on..." (with the edit still applied)
- "Stashing and re-running is overhead; the cause is obvious..."
- Reasoning about what caused the failure for longer than the test would take to run

---

## Why It Works

1. **It replaces narrative with an experiment.** Both wrong stories are generated by plausibility; the stash-and-rerun is a binary measurement that overrides plausibility in either direction, and it's explicitly cheaper than the storytelling it replaces.

2. **It closes the "different file" loophole.** The most common false acquittal rests on spatial distance — didn't touch that file, can't be me. Naming propagation through imports and shared state removes that intuition's authority.

3. **It closes the "timing" loophole symmetrically.** The most common false conviction rests on temporal proximity. The instruction attacks both biases with the same single test.

4. **It demands the result be stated.** Requiring "fails on clean baseline too" in the output makes skipping the experiment detectable rather than silent.

## Origin

After an assistant's small refactor, an integration suite started failing, and the assistant spent ninety minutes progressively deforming its own refactor to appease the failure — adding compatibility shims, reverting half the cleanup, re-adding a deprecated parameter. A developer finally ran the suite on a clean checkout: same failure. An expired test fixture certificate, nothing to do with any code. The refactor, originally correct, was merged in its mangled form because nobody wanted to touch it again.
