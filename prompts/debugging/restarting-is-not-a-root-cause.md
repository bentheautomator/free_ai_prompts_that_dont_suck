# Restarting Is Not a Root Cause

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents the AI from closing a bug with "restarted the server and it works now" while the cause remains unidentified and ready to recur.

**[Copy-paste ready version](../../install/restarting-is-not-a-root-cause.md)** — just the instruction block, no explanation.

## The Problem

Restart the dev server. Clear the cache. Delete `node_modules` and reinstall. Reboot the container. These rituals end a surprising number of AI debugging sessions, with the failure gone and the explanation absent. The bug stopped reproducing because some accumulated state got wiped — but *which* state, accumulated *how*, was never determined. The AI reports success; the underlying cause (a leak, a stale artifact being generated by a broken build step, corrupted state from a crash, an ordering dependency on a warm cache) is fully intact and on schedule to recur.

The seduction is that resets genuinely work, in the sense of making symptoms vanish, and they're zero-risk to perform. That makes them excellent *diagnostic* moves and terrible *conclusions*. "Reinstalling fixed it" contains real information — it localizes the problem to whatever the reinstall replaced — but the AI treats it as the end of the story instead of the best clue so far. Nobody asks the follow-up: what was wrong with the old state, and what process made it wrong?

The cost arrives on a delay. The bug returns next week (the state re-accumulates), now with a team trained to reach for the ritual instead of the cause, and a "fix" history full of restarts that documents nothing.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Restarting Is Not a Root Cause

NEVER close a bug with a restart, reinstall, cache clear, or reboot as the fix. A reset that makes the symptom vanish is a diagnostic clue about *where* the bad state lived — it is not an explanation of how the state went bad, and the cause will regenerate it.

- Use resets deliberately as experiments, not exorcisms: before wiping, capture the evidence (copy the bad state, note what's in the cache, save the logs), because the wipe destroys your only sample of the failure
- When a reset works, extract its information: what exactly did it replace? That set — the process memory, the cache contents, the installed packages, the build artifacts — is now your search space for the real cause
- Then answer the second question: what *produced* the bad state? A leak, a non-deterministic build, an interrupted write, a stale lockfile, code that only works from a cold start? That answer is the fix
- Distinguish one-off corruption (a crashed process left a lock file; cause known, no recurrence expected) from produced corruption (something keeps generating it); only the first may be closed after cleanup, and even then say which it was
- If you cannot determine how the state went bad, report the bug as *mitigated, not fixed*, with what you know about where the state lived — never as resolved
- "It works after a restart" appearing in your summary as the resolution means the investigation is unfinished

**Red flags that you're about to violate this:**
- "Cleared the cache and the issue is resolved..."
- "A fresh install fixed it — closing this out..."
- "Probably just a corrupted state thing, restart took care of it..." (corrupted by what?)
- "If it happens again we can dig deeper..."
- Wiping the bad state before capturing any of it
- Recommending the reset to the user as the fix rather than as a stopgap

---

## Why It Works

1. **It converts the ritual into an instrument.** "What did the reset replace?" turns the same zero-effort action from a conclusion into a localization step, so the AI's favorite move now feeds the investigation instead of ending it.

2. **It forces the production question.** Bad state has a producer; asking "what generated it?" is the difference between deleting the symptom and finding the bug, and the instruction makes that question non-optional.

3. **It protects the evidence.** Resets destroy the only copy of the failure; the capture-before-wipe rule preserves the sample that makes a real diagnosis possible later.

4. **It introduces "mitigated, not fixed."** Giving the AI an honest intermediate status removes the pressure to label an unexplained recovery as a resolution.

## Origin

A staging environment failed every few days with garbled API responses, and each time the assistant's remedy was the same: restart the service, confirm responses look correct, close the ticket. Fourth recurrence, a developer captured the process state before restarting: an in-memory template cache was being corrupted by a concurrent write during config reload. The bug was a missing lock, fixable in an afternoon — and had been wiped, along with all evidence, three times in a row by the ritual that kept "fixing" it.
