# Never Hand-Edit Generated Doc Sections

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents the AI from hand-editing auto-generated documentation that the next build run will silently obliterate.

**[Copy-paste ready version](../../install/never-hand-edit-generated-doc-sections.md)** — just the instruction block, no explanation.

## The Problem

The user says "fix the typo in the API reference," and the AI dutifully edits `docs/api/reference.md`. The fix is correct, the diff is clean, everyone moves on. Then someone runs `make docs`, the generator regenerates `reference.md` from the source docstrings, and the typo is back. Worse: if the AI made substantive edits — added a missing parameter description, documented a gotcha — that content is now gone, and nobody knows it existed, because the regeneration diff looks like noise.

AI assistants do this because generated files are indistinguishable from authored files unless you read the warnings, and the model's edit-the-file-the-user-pointed-at reflex is strong. Markers like `<!-- AUTO-GENERATED -->`, `@generated`, or "DO NOT EDIT" headers are skimmed past, especially when the marker is at line 1 and the typo is at line 400. Sometimes there's no marker at all, just a build script that nobody mentioned.

The damage compounds: edits to generated files survive until the next regen, which can be weeks. The fix works long enough for everyone to forget it, then evaporates.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Never Hand-Edit Generated Doc Sections

NEVER edit auto-generated documentation files or sections by hand. Find the source they're generated from and edit that, then regenerate if you can.

The problem: hand edits to generated docs survive only until the next build, then vanish without a trace, taking your fix and any later additions with them.

Rules:
- Before editing any doc file, check for generation markers: "AUTO-GENERATED", "DO NOT EDIT", `@generated`, "this file is generated by", or START/END marker comments around sections
- Also check beyond the file: a `docs` build target, generator scripts (`scripts/build-docs.*`, `make docs`), or repo instructions naming generated paths. Some generated files carry no in-file marker
- When you find the generator, trace the edit to its true source: docstrings, an OpenAPI spec, a template, frontmatter, a comment in the code. Fix it there
- If you can run the generator, run it so the generated output updates in the same change. If you can't, say exactly which command the user must run
- Marker-delimited sections (e.g., between `GENERATED_START`/`GENERATED_END`) are generated even when the rest of the file is hand-authored; edit outside the markers freely, inside never
- If the user explicitly insists on editing the generated file, warn once that the edit will be overwritten, then comply

**Red flags that you're about to violate this:**
- "The user pointed at this file, so this is the file to edit..."
- "It's a one-character typo, regeneration is overkill..."
- "I don't see the generator, so it's probably hand-maintained..."
- "I'll edit both the source and the output to be safe..." (fine only if the output matches what the generator would emit)
- "That DO NOT EDIT header is probably stale..."
- "Finding the template will take longer than just fixing it here..."

---

## Why It Works

1. **It fixes the durability failure, not the cosmetic one.** An edit to generated output is correct and doomed; an edit to the source is correct and permanent. Same effort, different half-life.

2. **The marker checklist catches what skimming misses.** Models read for content, not provenance. An explicit list of marker strings turns provenance into a cheap pre-edit grep.

3. **It covers unmarked generation.** Checking for build targets and generator scripts handles the worst case: generated files that don't announce themselves.

4. **Regenerating in-change keeps source and output atomic.** When source and stale output ship together, the repo lies until the next build; regeneration makes the change self-consistent.

## Origin

An assistant spent an afternoon enriching a CLI tool's command reference: better examples, clearer flag descriptions, a troubleshooting section. All of it went into `docs/commands.md`, which was generated from the argparse definitions by a release script. The next release regenerated the file, and four hundred lines of good documentation disappeared in a commit titled "release 2.9.0." It was rediscovered months later by someone reading old diffs, and re-keyed by hand into the docstrings where it should have gone the first time.
