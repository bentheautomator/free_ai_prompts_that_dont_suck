# Avoid Temporal Language in Docs

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents docs written from a single moment in time — "currently", "recently added", "coming soon" — that become misleading the moment that moment passes.

**[Copy-paste ready version](../../install/avoid-temporal-language-in-docs.md)** — just the instruction block, no explanation.

## The Problem

"The new caching layer currently supports Redis only; Memcached support is coming soon." Read that sentence two years after it was written. Is the caching layer still new? Did Memcached support arrive, or was it abandoned? "Currently" as of *when*? The sentence contains four claims and a timestamp for none of them, and the missing timestamp is load-bearing for every claim. Docs full of temporal language don't describe the system; they describe a snapshot, unlabeled, mixed in with sentences that are actually timeless.

AI assistants generate this constantly because they write from the perspective of the change they just made: the feature *is* new (today), the limitation *is* current (today), the roadmap item *is* planned (today, as far as the model can guess, which it often can't — "coming soon" in AI-written docs frequently describes things nobody has actually planned). The conversational register leaks into the archival medium.

The damage is subtle but pervasive: readers can't distinguish live facts from fossilized ones, so the whole doc's credibility decays to the credibility of its stalest sentence. "Soon" is the worst offender — it's a promise with no owner and no date, immortalized.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Avoid Temporal Language in Docs

NEVER write documentation that's only true from the vantage point of the day you wrote it. Docs are read in the future; write claims that are either timeless or explicitly dated.

The problem: words like "currently", "new", "recently", and "soon" smuggle an invisible timestamp into prose. The claim rots; the confident tone doesn't.

Rules:
- State facts plainly without temporal hedges: "Supports Redis" not "currently supports Redis". If Redis support ends, the doc needs editing either way; "currently" only adds doubt while it's true
- Never describe features as "new", "recently added", or "the latest". Tie facts to versions instead: "Available since v2.3" stays true forever
- Never write "coming soon", "planned", or "in a future release" unless the user told you it's planned; you are not authorized to make roadmap promises, and unscheduled "soon" is the longest word in software
- When a limitation is genuinely temporary and tracked, reference the tracker, not the calendar: "Not yet supported (see #512)" gives readers a live status source
- Replace "as of now"/"at the time of writing" with the actual version or date if the time-boundedness matters, or restructure so it doesn't
- "Currently" is sometimes honest in design docs and proposals, which are inherently dated artifacts; this rule is about reference docs, READMEs, and guides that claim present truth

**Red flags that you're about to violate this:**
- "Calling it new highlights the recent work..."
- "'Currently' is accurate, it does only support Redis right now..."
- "'Coming soon' softens the missing feature..."
- "Readers will know roughly when this was written..."
- "I'll mention the roadmap to be helpful..."
- "'As of this writing' covers me..."

---

## Why It Works

1. **It removes the invisible-timestamp dependency.** "Supports Redis" is verifiable against the code at any future date; "currently supports Redis" is verifiable only against the unstated date of writing. Stripping the hedge makes claims future-readable.

2. **Version anchors convert decay into permanence.** "New in v2.3" rots; "available since v2.3" is true in perpetuity. The single substitution captures the same information with an infinite shelf life.

3. **It blocks unauthorized promises.** "Coming soon" generated by a model is a roadmap commitment nobody made, published in the project's voice. Requiring user-confirmed plans (or a tracker link) keeps promises attached to owners.

4. **Tracker links outsource freshness.** A doc can't know the current status of a limitation, but it can point at the one place that does. The reference stays correct even as the status changes.

## Origin

A library's README promised "Windows support coming soon" in an AI-drafted limitations section; no maintainer had ever planned Windows support. The line attracted a steady drip of "any update on Windows?" issues for over a year, each requiring a maintainer to explain that "soon" had been an editorial flourish. The eventual fix replaced one sentence of optimism with one sentence of fact ("Linux and macOS only; Windows is not planned, see #88") and the issue traffic stopped within a release cycle.
