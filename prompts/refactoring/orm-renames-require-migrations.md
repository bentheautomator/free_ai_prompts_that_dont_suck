# ORM Renames Require Migrations

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents the AI from renaming ORM model attributes as if they were ordinary variables, when each one is bolted to a database column.

**[Copy-paste ready version](../../install/orm-renames-require-migrations.md)** — just the instruction block, no explanation.

## The Problem

An ORM model looks like a class, so assistants refactor it like a class. Rename `Customer.cust_nm` to `Customer.name`, update every Python/Ruby/TypeScript reference, done. Except that attribute wasn't a variable; it was the mapped name of a column in a production table, and the table didn't get the memo. Depending on the framework, the result is an immediate crash ("column customers.name does not exist"), a generated migration that *drops* `cust_nm` and *adds* `name`, silently discarding every value in the column, or an autogenerated diff that someone applies without reading because the assistant said it was a rename.

The drop-and-add migration is the killer. Several ORMs cannot tell a rename from a delete-plus-create, so the autogenerated migration is destructive while looking routine. Models compound this by trusting the autogeneration: "I renamed the field and generated the migration" sounds like a completed, careful task, and it can describe a data-loss event.

Beyond the column itself, ORM attribute names leak everywhere strings reach: query filters (`order_by("cust_nm")`), serializer field lists, admin configurations, raw SQL fragments, and index definitions. A "simple" model rename is a multi-surface migration project wearing a one-line disguise.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### ORM Renames Require Migrations

NEVER rename an ORM model attribute, model class, or table mapping as a pure code change. Every mapped name is bound to a database object; renaming the code side requires either an explicit column mapping or a deliberate, rename-aware migration, chosen and stated up front.

- The safest cleanup is mapping, not migration: rename the attribute in code and pin the existing column name explicitly (`db_column="cust_nm"`, `@Column(name=...)`, `field :name, as: ...`). Code gets readable; the schema and all data stay untouched.
- If an actual schema rename is wanted, write the migration as a RENAME operation (`RenameField`, `rename_column`, `ALTER TABLE ... RENAME COLUMN`). Never accept an autogenerated migration without reading it: several ORMs autogenerate renames as drop-column-plus-add-column, which destroys the data.
- Read every generated migration aloud in your summary: name the operations it contains. "AddField + RemoveField" in response to a rename is the alarm, not the answer.
- Renames also break the string surfaces: `filter`/`order_by` arguments, `values()`/`only()` lists, serializer `fields`, admin `list_display`, raw SQL, index and constraint definitions, and any report or ETL query in the repo. Search for the old name as a string and fix or flag every hit.
- Table-name and model-class renames carry the same rules plus foreign-key and migration-history implications; treat them as schema projects, not refactors.
- If other services or analysts query this database directly, the column name is a shared contract; flag the rename to the user instead of performing it.

**Red flags that you're about to violate this:**

- "I'll rename the field and regenerate the migration; the ORM handles it."
- "The autogenerated migration looks standard, so I'll include it."
- "It's just an attribute rename; the database layer is abstracted away."
- "Nothing else queries this table directly, most likely."
- "The old column name was inconsistent with our conventions, so this is a cleanup."

## Why It Works

1. **It offers the zero-risk alternative first.** Most "rename the field" desires are readability desires, and explicit column mapping satisfies them with no schema change at all; given the option, the model stops needing the dangerous path.
2. **It teaches the drop-and-add tell.** The model trusts autogenerated migrations; knowing that "RemoveField + AddField" is what data loss looks like turns the migration review from ritual into detection.
3. **Reading the migration aloud forces inspection.** A model required to enumerate the operations cannot ship a migration it never parsed, which is otherwise exactly what happens.
4. **The string-surface search extends the rename to where ORMs actually break.** Filters and serializer lists fail at runtime, not import time; putting them in the checklist catches the failures tests usually miss.

## Origin

A schema-consistency pass renamed `shipped_dt` to `shipped_at` on an orders model. The autogenerated migration removed the old column and added the new one, which the assistant summarized as "renamed field with migration." Staging had no data worth noticing. Production had four years of ship dates, and the migration ran before anyone read it. The column was restored from the previous night's backup, minus a day of shipments that had to be reconstructed from carrier emails.
