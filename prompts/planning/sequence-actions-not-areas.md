# Sequence Actions, Not Areas

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents mistaking a list of places the work happens for a sequence of work to do.

**[Copy-paste ready version](../../install/sequence-actions-not-areas.md)** — just the instruction block, no explanation.

## The Problem

A common shape of assistant plan: "1. Backend changes. 2. Frontend changes. 3. Database. 4. Tests." Look closely — that's not a plan, it's a *map*. It lists the territories the work will pass through, in no particular order beyond the order they came to mind. Nothing in it says what must exist before what, where the natural checkpoints fall, or what can be verified when. It's a table of contents for a book about the plan.

The difference matters at execution time. A sequence has dependency logic: "add the column, backfill it, deploy the read path, then the write path, then enforce the constraint" — each step enabled by the previous, each leaving a verifiable state. An area list has none, so execution order defaults to list order, and list order was generated by salience, not dependency. That's how the frontend gets built against an API that doesn't exist yet, the tests get written last against whatever happened to ship, and "database" — silently the foundation of all of it — sits at position three because it came to mind third.

Area lists survive because they look organized and are easy to nod at. The test that kills them: can any step on this list be *finished*? "Backend changes" can't be finished — it's a region, not an action. If the steps don't have completion states, the plan doesn't have steps.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Sequence Actions, Not Areas

NEVER present a list of areas ("backend, frontend, tests") as a plan. A plan is a sequence of actions ordered by dependency, where each step can be finished and verified. An area cannot be finished — it can only be visited.

The core problem: area lists look organized, so they pass for plans — but their order is the order things came to mind, and executing salience-order instead of dependency-order builds consumers before the things they consume.

- Write steps as actions with completion states: "add nullable `archived_at` column and deploy" can be done and checked. "Database changes" cannot.
- Order by dependency, then state the dependency: "step 3 needs the endpoint from step 2." If no step depends on any other, ask whether you've actually decomposed the work or just categorized it.
- Apply the finishability test to every line: could you ever announce this step *complete*? If not, it's a heading, not a step — break it into the actions hiding under it.
- Interleave areas when dependencies demand it. Real sequences hop: schema, then API, then a slice of UI, then back to schema for the next field. A plan that visits each area exactly once is suspicious.
- It's fine to *also* group the summary by area for readability — after the sequence exists, not instead of it.

**Red flags that you're about to violate this:**
- "Step 1: backend updates. Step 2: frontend updates..."
- "I'll just work through it layer by layer..." (in what order within layers, and why?)
- "The plan covers all the areas involved..." (coverage isn't sequence)
- "Order doesn't really matter for this one..." (then why is the frontend before the API it calls?)
- "Tests" (as an entire step, positioned last, every time)

---

## Why It Works

1. **The finishability test is mechanical.** "Can this step be declared complete?" instantly separates actions from headings, with no judgment required. Headings fail it; real steps pass it. An assistant can self-apply it line by line.

2. **It forces dependency order to be computed, not defaulted.** Stating "step 3 needs step 2's output" requires actually deriving the dependency graph — the analysis that area lists let everyone skip. Wrong build order mostly comes from never having asked the question.

3. **It exposes fake decomposition.** Categorizing work by region feels like progress but transmits no decisions. Requiring completion states and dependencies makes a hollow plan visibly hollow at review time, when it's still free to fix.

## Origin

A plan for a permissions overhaul read: "1. Update models. 2. Update API. 3. Update UI. 4. Tests. 5. Migration." Approved — it covered everything. Execution followed list order, which put the migration *last*: the models and API were rewritten against permission tables that didn't exist yet, developed for days against hand-seeded local data. When the migration was finally written, the real data's legacy roles didn't map to the new model cleanly, forcing schema revisions that rippled back through steps 1-3. As a sequence, "migration" was obviously step one. As an area, it was just item five.
