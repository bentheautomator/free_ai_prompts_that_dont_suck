# Check the Lockfile Before Package Commands

> **Works with:** All AI coding assistants (Claude Code, Cursor, Windsurf, Copilot, Cline, Aider)

> Prevents AI from assuming npm when the lockfile on disk says pnpm, yarn, bun, uv, or poetry.

**[Copy-paste ready version](../../install/check-the-lockfile-before-package-commands.md)** — just the instruction block, no explanation.

## The Problem

There is a `pnpm-lock.yaml` in the repo root. The AI runs `npm install` anyway, because npm is the statistical default of its training data and the lockfile check never happened. Now there's a `package-lock.json` polluting the repo, a `node_modules` resolved by the wrong algorithm, possibly broken workspace links, and a diff the user has to clean up before they can even start the actual task.

The same failure has a costume for every ecosystem: `pip install` in a `poetry.lock` project, `pip` where the repo uses `uv`, `yarn add` in a bun repo, `npm run` in a workspace that needs `pnpm --filter`. The evidence is always one `ls` away — lockfiles exist precisely to declare the package manager — but the AI's prior is strong enough that it answers from instinct instead of from disk.

Mixed lockfiles aren't just clutter. CI that runs `pnpm install --frozen-lockfile` will pass while the local `node_modules` came from npm, producing "works on my machine" bugs with extra steps. And every accidental `package-lock.json` committed to a pnpm repo becomes a trap for the next contributor.

## The Instruction

Copy everything between the horizontal rules into your instructions file:

---

### Check the Lockfile Before Package Commands

NEVER run a package manager command without first identifying the project's actual package manager from the files on disk. The default in your head is npm or pip; the truth is in the lockfile.

Using the wrong manager creates duplicate lockfiles, wrongly-resolved dependencies, and broken workspaces — cleanup the user didn't ask for.

**Before any install, add, remove, or run command:**
- Check for lockfiles: `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `bun.lockb`/`bun.lock` → bun, `package-lock.json` → npm, `poetry.lock` → poetry, `uv.lock` → uv, `Pipfile.lock` → pipenv, `Cargo.lock`/`go.sum` → you're not in JS anymore
- Check `package.json` for a `packageManager` field or engines constraint — it overrides guesswork entirely
- Check README or CONTRIBUTING for explicit setup commands before inventing your own
- Use the same manager for every subsequent command in the session — no mixing `pnpm install` with `npm run build`
- If two lockfiles coexist, ask which one is authoritative instead of picking the one you like
- Never commit a lockfile generated by a manager the project doesn't use

**Red flags that you're about to violate this:**
- "I'll just npm install this real quick..."
- "It's a Node project, so npm is fine..."
- "pip and poetry basically do the same thing here..."
- "The command is equivalent across managers anyway..."
- "I don't see a lockfile in this file listing" — when you never actually listed the root
- Typing an install command before any `ls` of the project root this session

---

## Why It Works

1. **It replaces a prior with a lookup table.** The mapping from lockfile to manager is mechanical and complete. There is no scenario left where "I'll assume npm" is the rational move.

2. **It names `packageManager` as the trump card.** Corepack-era projects declare their manager in `package.json`; pointing the AI at that field resolves ambiguous cases without a question.

3. **It forbids mid-session mixing.** Half the damage comes from the second command, not the first — installing with pnpm and then running scripts via npm. Making consistency explicit closes that gap.

4. **It handles the two-lockfile edge case with a question, not a coin flip.** Repos in migration are exactly where a confident guess does the most harm.

## Origin

A contributor asked the AI to add one dev dependency to a pnpm workspace. The AI ran `npm install --save-dev`, which generated a 14,000-line `package-lock.json`, flattened `node_modules`, and broke the symlinked workspace packages. The dependency itself took ten seconds; restoring the workspace, deleting the rogue lockfile, and re-running `pnpm install` took the rest of the morning — and the bad lockfile still made it into one commit, where it confused dependabot for a week.
